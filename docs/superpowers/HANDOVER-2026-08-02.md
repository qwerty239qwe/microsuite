## The one lesson that matters most

**Mocked-subprocess tests verify only that you construct the commands you
*intended*. They say nothing about whether those commands are correct.**

The mothur work shipped fourteen defects past a fully green test suite. Every
single one produced a *complete, well-formed, wrong result* rather than an error:
a table with one column instead of five, taxonomy consensus over 3 of 68
sequences, chimeric abundances surviving into every downstream number.

They were found only by running the real tool and asserting on the biology.

Concretely, for any external-tool backend:

- Capture real stdout as fixtures. Never hand-write them. See
  `tests/fixtures/mothur/README.md` for the convention — it has a "these are
  evidence, never edit them" rule, and that rule caught real bugs.
- **Fixtures captured on toy input can be actively misleading.** Four mothur
  commands behave *differently* on the pipeline's real configuration (aligned
  input, grouped count table) than on convenient toy data. One inverts which
  files it emits. Capture in the configuration the code actually uses.
- Write an end-to-end smoke test that asserts on results, not exit status. An
  exit-0-only smoke test would have passed on all five of the worst defects.
  `tests/integration/test_mothur_smoke.py` is the model: deterministic generated
  data, no committed fixtures, assertions on the biology.
- When adding a data-flow test, **deliberately break the data flow and confirm
  the test fails**, then revert. A hand-off test that passes against scrambled
  hand-offs is worse than none.

## Environment gotchas

These each cost real time to find.

**Docker mounts from Git Bash.** `docker run -v "/tmp/x:/data"` silently mounts an
*empty* directory — Docker Desktop's WSL2 backend resolves `/tmp` inside its own
VM. Use the Windows path and `MSYS_NO_PATHCONV=1`:

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "<windows-temp>/x:/data" image ...
```

**`gh` is not installed.** To use the GitHub API, pull the credential from Git
Credential Manager and pipe it straight into curl so it never lands in a log:

```bash
{ printf 'protocol=https\nhost=github.com\n\n'; } | git credential fill 2>/dev/null \
  | awk -F= '/^password=/{print substr($0,10)}' | { read -r TOK; curl -s -H "Authorization: Bearer $TOK" ... ; }
```

**pytest suppresses the summary.** `addopts = "-q"` in `pyproject.toml` means no
"N passed" line. Use `--junitxml` and parse the XML for reliable counts.

**`ty check` needs the full environment.** Run `uv sync --all-extras --locked`
first, or you will see a spurious `biodbs` unresolved-import diagnostic that CI
does not have.

**Commit messages must not carry `Co-Authored-By:` or `Claude-Session:`
trailers.** User instruction.

## Test baseline

Linux CI: `test_metadata_models` (3), `test_metadata_redact` (1),
`test_run_fastp_multiqc_script` (4), `test_runtime_container` (2),
`test_system_doctor` (1). They are POSIX-path and `os.getuid` assumptions.

**But do not let "pre-existing" become a blind spot.** In this session a merge
introduced `primer.py`, which failed `ruff format --check` and `ty check`, and
those failures were dismissed as "pre-existing baseline" for the entire session.
CI on `main` was red the whole time. Verified: `546ef0c` was green, `4ce99c9`
(the merge) was red.

**Always check CI status before claiming anything is ready.** Local green is not
CI green.

## The consumer project

A private research repository — ask the maintainer for its location — consumes
microsuite heavily across ~21 study accessions. It is the best source of truth
about what microsuite gets wrong.

**It maintains `docs/microsuite_complaints.txt`** — 20 numbered items, 6 already
marked MITIGATED by earlier work. That file should be an input to every release,
not something rediscovered by audit.

Its workarounds are the flaw list. A script there that post-processes microsuite
output, or reimplements something microsuite offers, is direct evidence of a gap.
`scripts/python/finalize_microsuite_diversity.py` and
`scripts/r/run_maaslin2_repeated_measures.R` are the two clearest examples.

## Process notes

- The user prefers being asked when a decision is genuinely theirs — version
  numbers, release timing, scope boundaries — and prefers you proceed without
  asking on conventional defaults.
- Subagent-driven development worked well here: fresh implementer per task, a
  separate reviewer per task, then a whole-branch review. The separate reviewer
  caught defects the implementer's self-review missed every single time.
- When a reviewer reports a finding, **verify it yourself before acting**. In this
  session a reviewer's Critical finding (N1) turned out to be unreproducible, and
  another (N3) was unconfirmable but worth fixing anyway. Both judgments needed
  running the code, not reading it.
